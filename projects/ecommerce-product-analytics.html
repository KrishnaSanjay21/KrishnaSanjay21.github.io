E-commerce Product Analytics

A GA4-style warehouse that transforms raw behavioral events into tested dimensions, facts, and six decision-ready marts for funnel, revenue, acquisition, retention, lifetime value, and product affinity.

The problem

Event data becomes useful only after its grain and metrics are trusted.

Raw analytics exports are nested, repetitive, and easy to miscount. This project defines stable dimensions and facts before calculating product metrics, so sessions, orders, revenue, customers, and funnel stages have consistent definitions across every downstream question.

Modeling principle

Each mart names the decision it supports. SQL structure follows the business question instead of creating generic tables without a consumer.

Warehouse architecture

Two execution paths share one analytics contract.

  1. Generate or query events

    The local path creates deterministic GA4-like events in SQLite; the cloud path targets Google's obfuscated public GA4 e-commerce sample in BigQuery.

  2. Build conformed models

    Dimensions and facts establish user, session, product, event, and order grain before analysis.

  3. Run quality assertions

    Check uniqueness, accepted values, order completeness, revenue agreement, and monotonic funnel counts.

  4. Materialize marts

    Build funnel, daily KPI, channel, customer LTV, cohort retention, and product-affinity tables.

  5. Publish artifacts

    Export every mart to CSV and render a consolidated HTML analytics summary.

Decision products

Six marts answer six distinct product questions.

  • Funnel: where sessions abandon view, cart, checkout, and purchase stages.
  • Daily KPIs: revenue, orders, users, sessions, and average order value over time.
  • Channels: which acquisition sources bring converting and valuable traffic.
  • Customer LTV: who merits retention investment based on observed orders and revenue.
  • Cohorts: how engagement changes after acquisition.
  • Product affinity: which products co-occur and may support bundling or cross-sell.

Engineering evidence

Reproducibility is part of the warehouse design.

The local build uses Python 3.10+ and the standard library, creates the database from scratch, runs SQL in dependency order, validates results, and emits reports. Five end-to-end tests verify passing quality checks, monotonic funnel counts, exact order-revenue reconciliation, full LTV user coverage, and the presence of repeat purchasers.

Limits & next steps

The local fixture is not current store performance.

  • The deterministic SQLite data exists for development and tests; its metrics are synthetic.
  • The BigQuery path targets the public obfuscated sample from 2020-11-01 through 2021-01-31.
  • Cloud execution volume, bytes processed, and business impact must be measured before being claimed.
  • A production warehouse needs orchestration, freshness checks, identity resolution, consent handling, and metric ownership.
Next milestone

Execute and profile the BigQuery path, add incremental models and freshness assertions, then connect a dashboard whose decisions map directly to the documented marts.
